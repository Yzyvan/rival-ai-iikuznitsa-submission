# Vilar Tracker · HTTP v1

Канбан использует шлюз на том же origin, что и страница. Все примеры ниже синтетические. Идентификаторы непрозрачны. Число `version` относится к самой карточке, а `result_version` — к сданному результату. Сервер определяет область видимости по установленной пользовательской сессии.

## Команды канбана

| Действие | Метод и путь | Результат |
| --- | --- | --- |
| Список | `GET /tracker/api/tasks` | `{rows, can_create}`. Фильтры `q`, `assignee_person_id` и `column` необязательны. |
| Карточка | `GET /tracker/api/tasks/{id}` | Текущая карточка по ID. Набор доступных колонок и действий приходит в ответе. |
| Участники | `GET /tracker/api/people` | `{rows:[{id,name}],self_id}`. |
| Создание | `POST /tracker/api/tasks` | HTTP 201 с созданной карточкой. Поддерживаются `assign`, `project`, `self`, `meeting`. |
| Перенос, правка, изменение срока | `POST /tracker/api/tasks/{id}/move`, `/edit`, `/reschedule` | HTTP 200 и актуальная карточка. Перенос принимает `column`, правка — название и редактируемые поля, перенос срока — `due_date` и необязательное `due_time`. |
| Напоминание или отмена создания | `POST /tracker/api/tasks/{id}/remind`, `/undo-create` | Напоминание возвращает карточку. Отмена возвращает `{id,undone:true}`. |

Для записи используются JSON и заголовок `Idempotency-Key`. При потере ответа клиент повторяет те же данные с прежним ключом. Изменения карточки передают `expected_version`. Ответ 409 означает, что клиенту нужно перечитать карточку перед новым решением. При отсутствии сессии возвращается 401, при недостаточных правах — 403, недоступная карточка может вернуть 404.

Пример тела создания поручения:

```json
{"kind":"assign","title":"Согласовать время встречи","assignee_person_id":"demo-person","column":"new"}
```

Пример полей ответа HTTP 201:

```json
{"id":"demo-task","title":"Согласовать время встречи","assignee_person_id":"demo-person","version":1,"status":"open","column":"new"}
```

Для переноса этой карточки в работу передайте `{"column":"in_progress","expected_version":1}`. Полная форма ответов задач и справочника описана типами `TaskRecord`, `TaskList` и `People` в [клиенте HTTP](../../integrations/tracker/transport/bindings.ts).

## Доставка и сдача результата

1. Процесс интеграции получает одну выдачу через `POST /v1/dispatch/claim`. Результат содержит ID выдачи, дела и шага, адресата, версию материала и токен конкретной попытки. При пустой очереди возвращается 204.
2. После сохранения карточки клиент посылает `POST /v1/dispatch/{id}/receipt` для той же попытки. Квитанция означает, что поручение доставлено. Шаг остаётся открытым.
3. Сотрудник читает `GET /tracker/api/mine?step={id}` и отправляет `POST /tracker/api/result` с `dispatch_id` и событием, в котором указаны дело, шаг, ссылка на результат, версии и редакция. Шлюз обращается к `POST /v1/events` с контекстом выдачи и сотрудника. Ответ 202 подтверждает приём события. Статус применения читается через `GET /v1/events/{id}`.
4. Доска перечитывает `GET /tracker/api/board`. На проверку поступает конкретная версия с автором и принимающим. Повторное чтение после 202 безопасно.
